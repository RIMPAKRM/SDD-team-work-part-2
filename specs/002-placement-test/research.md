# Research: Тест на определение уровня

## R1. Состояние теста

**Decision**: Локальный state компонента `TestPage` для сессии (фаза `intro | running | result`, текущий вопрос, массив ответов). Персистится только финальный результат — через zustand persist (`src/store/testResult.js`, ключ `test-result`).

**Rationale**: Прогресс незавершённого теста по спеке не сохраняется — отдельный стор нужен лишь для результата; держать сессию в localStorage избыточно.

## R2. Банк вопросов

**Decision**: Ровно 15 фиксированных вопросов в `src/data/questions.json`, порядок = нарастающая сложность, без рандомизации и без перемешивания вариантов.

**Rationale**: Спека требует «15 вопросов» и пороги по счёту; фиксированный набор проще валидировать и соответствует «маленькой странице». Большой банк с сэмплингом — избыточен для вымышленных данных.

## R3. Скоринг и пороги

**Decision**: `score = count(answers[i] === questions[i].correctIndex)`; маппинг в уровень в `lib/scoring.js`: 0–4 Beginner, 5–8 Elementary, 9–12 Intermediate, 13–15 Upper-Intermediate. Описание уровня — короткий текст в данных.

**Rationale**: Пороги зафиксированы спекой (FR-003); вынесение в lib позволяет менять их без правки компонентов.

## R4. Маппинг уровень → группа

**Decision**: `src/data/level-group-map.json`: `Beginner→group-1, Elementary→group-2, Intermediate→group-3, Upper-Intermediate→group-4`. Рекомендация берёт уровень/преподавателя/расписание из общего `src/data/groups.json` (фича 001), занятость — по активным пробным записям из `trial_signups` в localStorage (общий ключ фичи 001; поля `enrolled` в данных нет).

**Rationale**: `groups.json` — общий ресурс по конституции (Module Isolation разрешает shared `data/`); дублировать данные групп в модуле теста нельзя — расходились бы версии. `trial_signups` читается напрямую как общий ключ — без импорта кода модуля 001.

## R5. Переход «рекомендация → запись»

**Decision**: URL-параметр: кнопка ведёт на `/?group=<groupId>` — страница расписания (фича 001) живёт на маршруте `/`. Параметр `group` передаётся на будущее: текущая реализация `SchedulePage` его не обрабатывает (подсветка/предвыбор — возможная доработка 001).

**Rationale**: Чистый контракт между модулями через URL — без общего стора и прямых импортов модуля в модуль.

## R6. Маршрут и точка входа

**Decision**: Маршрут `/test` → `TestPage` (модуль `src/modules/test/`). Точки входа: общий компонент `src/components/TestBanner.jsx`, добавляемый на `SchedulePage` (фича 001) одной строкой; также прямая ссылка `/test`.

**Rationale**: Конституция — модуль изолирован в `src/modules/test/`; баннер — shared-компонент в `components/`, так как он относится к сайту, а не к модулю расписания.

## R7. UX формы теста

**Decision**: Один вопрос за экран: текст вопроса, 4 radio-варианта, кнопки «Назад»/«Далее» (на последнем — «Узнать результат», активна при ответе на все), прогресс-бар «N/15».

**Rationale**: Пошаговый формат читаем на мобильных и соответствует acceptance-сценариям спека.

## R8. Повторный визит

**Decision**: При наличии сохранённого `TestResult` `TestPage` стартует сразу с фазы `result` + кнопка «Пройти заново» (сбрасывает сессию, не результат — результат перезапишется при завершении).

**Rationale**: US3 спеки; минимум состояний — один persisted-объект.

## R9. Зависимость от фичи 001

**Decision**: Фича 001 уже реализована. 002 читает `src/data/groups.json` и `trial_signups` (localStorage) и направляет на `/?group=`. Код модуля 001 не импортируется — связь только через общие данные и URL.

**Rationale**: Общие данные зафиксированы контрактом ui-contracts.md фичи 001; `trial_signups` — публичный ключ её хранилища.

## R10. Тестирование

**Decision**: Ручная проверка по `quickstart.md`; юнит-тесты опциональны.

**Rationale**: Тестовые зависимости не в requirements.txt; сценарии проверяемы вручную.
